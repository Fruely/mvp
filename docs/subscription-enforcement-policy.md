# Subscription Enforcement Policy

## 1. Purpose

Этот документ фиксирует **предлагаемую будущую** продуктово-техническую политику Freuly: какие последствия могут наступать после окончания тарифа, в льготном периоде и при длительной неактивности подписки — в части видимости профиля, заявок, контактов, кабинета и бонусов ранних специалистов.

**Важно:** описанная ниже логика **не является текущей реализацией** в коде, базе данных или API. На момент написания документа enforcement в продукте **не включён** в полном объёме; документ служит ориентиром для согласования с продуктом, юридическим блоком и будущей разработкой.

## 2. Current state

На текущий момент (MVP / ранняя фаза):

- **Оплата не принимается** — платёжный провайдер и checkout не подключены.
- **Ранний доступ:** типичный сценарий для первых специалистов — бесплатное размещение в рамках `early_access` (и смежных статусов), без оплаты на платформе.
- **Публичная страница `/pricing`** носит **информационный** характер: будущие тарифы и сроки будут сообщены заранее.
- **Кабинет:** статус подписки отображается из канонического источника `specialist_plan` (`plan_code`, `plan_status`, даты, при необходимости `grace_until`); есть UI-notices на основе display-state helper.
- **Публичная видимость специалиста** определяется полями профиля и модерацией (`is_visible`, `is_active`, `status` специалиста и т.п.) — **не** напрямую от «оплачен ли тариф» в текущей модели.
- **Ограничение контактов в заявках:** реализовано узко — контакты скрываются при **`plan_status = expired`** (и не расширяется этим документом в коде).
- **Профили не удаляются автоматически** по истечении подписки; массового или скрытого «физического» удаления как стандарта нет.

## 3. Core principles

Будущая enforcement-логика должна опираться на принципы:

1. **Никаких внезапных списаний** — списания только после явного согласия, понятного биллингового цикла и работающей оплаты; до этого момента платежи на платформе отсутствуют.
2. **Никаких внезапных отключений без предупреждения** — смена режима доступа/видимости сопровождается заранее оговорёнными уведомлениями (email, Telegram, in-dashboard).
3. **Специалист заранее видит сроки** — `expires_at`, `grace_until` и статусы отражаются в кабинете; расписание предупреждений согласуется с продуктом.
4. **Физическое удаление профиля не используется как стандартная мера** — предпочтительны состояния **скрыт** / **архив** / **деактивирован** с сохранением данных в соответствии с политикой хранения и GDPR.
5. **История сохраняется** — заявки, согласия, журнал важных действий и содержимое профиля (в рамках правовых оснований) не «стираются» ради enforcement без отдельного правового обоснования.
6. **Бонусы ранних специалистов отделены от факта оплаты** — льготы за ранний вход не должны произвольно смешиваться с «оплатил/не оплатил» без явных правил.
7. **Согласованность с правилами для специалистов** — любые санкции и ограничения должны быть предсказуемыми и отражены в обновлённых правилах размещения / оферте.

## 4. Proposed future statuses

Ниже — **предлагаемая** схема статусов плана (`plan_status` или эквивалент). Точные имена в БД и переходы будут уточнены при внедрении.

| Статус | Смысл | Публичная видимость профиля | Контакты в лидах | Новые заявки | Редактирование кабинета | Влияние на бонусы |
|--------|--------|------------------------------|------------------|--------------|-------------------------|-------------------|
| **early_access** | Бесплатный ранний доступ, без оплаты | Как сейчас по правилам публикации | Обычно полные | Да | Да | Бонус «ранний» активен по правилам программы |
| **trialing** | Пробный платный/условный период (когда появится оплата) | По правилам публикации | Обычно полные | Да | Да | По правилам акции |
| **active** | Активная подписка / доступ оплачен или предоставлен по договору | По правилам публикации | Полные | Да | Да | Не отключается только из-за статуса «active» |
| **grace_period** | Льготный период после окончания оплаченного/активного срока | **Предлагается:** оставаться видимым | **Предлагается:** видимы | **Предлагается:** да | Да | Бонусы не снимаются «в ноль» в первый день просрочки |
| **expired** | Срок доступа истёк, льгота исчерпана (после grace или по политике) | Зависит от следующего шага (см. timeline) | Могут быть скрыты | Могут быть ограничены | **Предлагается:** ограниченно (например, только подписка/поддержка) | Могут быть заморожены по правилам |
| **limited** | Промежуточный режим: профиль частично в каталоге или с урезанным функционалом | **Предлагается:** видимость возможна, но с ограничениями | Ограничены | Ограничены или нет | Частично | Бонусы могут быть приостановлены |
| **hidden** | Профиль скрыт из публичной выдачи / каталога | Не показывается в поиске/каталоге | Н/п или только история | Нет новых публичных заявок | Да (восстановление, поддержка) | Сохранение условий бонуса — по политике |
| **archived** | Учётная запись/профиль в архивном состоянии, без активного предложения услуг | Нет публичной витрины | Нет | Нет | Минимальный или только экспорт/поддержка | По политике программы |
| **cancelled** | Подписка/договор прекращён по инициативе специалиста или платформы (по правилам) | По сценарию отмены | По сценарию | Обычно нет | По сценарию | По политике |

*Примечание:* строки «предлагается» отражают целевую модель, а не обязательства перед пользователями до публикации финальных правил.

## 5. Proposed timeline after period end

**Снова: это proposed / future logic, не текущая активная логика в проде.**

### До `expires_at`

- **За 14 дней:** мягкое уведомление (напоминание о дате окончания периода).
- **За 7 дней:** заметное предупреждение в dashboard, на странице подписки и при необходимости на странице заявок.
- **За 1 день:** финальное предупреждение с явной датой.

### После `expires_at`

- **Дни 0–3 (`grace_period`):** профиль **предлагается** оставить **видимым**; новые заявки **предлагается** принимать; контакты в лидах **предлагается** показывать; в UI — усиленное предупреждение о завершении льготы.
- **Дни 4–10 (`limited`):** профиль **может** оставаться видимым с ограничениями; контакты и/или новые заявки **могут** быть ограничены (конкретика — в ТЗ и правилах).
- **После дня 10 (`hidden`):** профиль **предлагается** скрыть из публичной выдачи; **кабинет и данные сохраняются** для поддержки и восстановления.
- **Конец расчётного биллингового месяца или после ручной проверки:** переход в **`archived` / `deactivated`** при необходимости — **без** физического удаления как нормы.

Переходы по календарю потребуют согласования с юридическим текстом, часовыми поясами и фактическим способом определения «дня 0».

## 6. Bonuses for early specialists

**Целевая модель (будущее):**

- Программы вида **«первые 50 / первые 100»** специалистов получают бонусы (видимость, метки, приоритет в подборках и т.д.) — точный состав определяется продуктом.
- **Бонус не обнуляется мгновенно** из-за одного календарного дня после `expires_at`, если действует осмысленный **grace for bonuses** (отдельно или совпадающий с `grace_period`).
- При **длительной** неоплате / неактивности подписки бонус может быть **заморожен**, **приостановлен** или **утрачен** — только если это **явно** прописано в правилах и доведено до специалиста заранее.
- **Потеря бонусов** не должна маскироваться под «удалили профиль»; **физическое удаление профиля** не является способом «забрать бонус».

## 7. Required product/legal prerequisites

Перед включением полноценного enforcement необходимо как минимум:

- Обновлённые **правила для специалистов** и публичная оферта / договорная база.
- Зафиксированное **согласие** специалиста с условиями (чекбокс, версионирование правил).
- Определённый **billing period** и понятные даты продления/окончания.
- Выбранный **платёжный провайдер** и процесс checkout.
- **Счета / налоги** (хотя бы на уровне MVP для целевой юрисдикции).
- Каналы уведомлений: **email**, при необходимости **Telegram**, **in-dashboard**.
- **Ручной override** в админке для исключительных случаев.
- **Audit log** изменений статуса подписки и видимости.
- **Privacy / GDPR** review для хранения, скрытия и архивации данных.

## 8. Technical building blocks needed later

Для реализации политики позже потребуется, в том числе:

- Интеграция **payment provider** и обработка webhooks / billing events.
- Сервис (или модуль) **переходов статусов** подписки с явными правилами и идемпотентностью.
- **Cron / scheduled jobs** для проверки дат (`expires_at`, `grace_until`) и мягких переходов.
- **Админские экраны** и API для ручных изменений и просмотра истории.
- Расширенная **система уведомлений** (шаблоны, расписание, отписка где применимо).
- **Audit log** в БД или внешнем хранилище.
- При необходимости — отдельные поля для **bonus state** / программы раннего доступа.
- Автоматические и интеграционные **тесты** на переходы статусов и граничные даты.

## 9. Explicit non-goals for now

На текущем этапе **не делаем** (и этот документ не требует):

- Подключение оплаты, Stripe/PayPal и т.п.
- Скрытие профилей из каталога **только** на основании этого документа.
- Изменение логики лидов, `isContactsLock`, публичных API видимости.
- Удаление специалистов или «жёсткая» зачистка данных.
- Блокировка входа в кабинет как стандартная мера MVP.
- Любые изменения схемы БД или прод-кода **в рамках задачи «только документация»**.

## 10. Recommended implementation order

Рекомендуемый порядок будущих работ (подлежит уточнению при планировании):

1. Финализация **правил и юридических формулировок**.
2. Отображение в админке **состояния подписки и бонусов** (read-only или с ручными правками).
3. Внедрение **расписания уведомлений** (без автоматических санкций, при необходимости).
4. Подключение **платёжного провайдера** в тестовом / выключенном режиме.
5. **Ручные** переходы статусов под контролем админки + audit log.
6. **Автоматические** переходы по датам (cron) после стабилизации ручного режима.
7. Поведение **`limited` / `hidden`** в каталоге и поиске.
8. Правила **приостановки / утраты бонусов** с прозрачным UX.
9. **Аналитика** и биллинговые метрики для операционного контроля.
