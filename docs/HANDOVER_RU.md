# Передача проекта Freuly — руководство для нового разработчика и владельца

Документ описывает устройство проекта **без раскрытия секретов**. Значения переменных окружения и токены в репозиторий не помещать.

---

## 1. Обзор продукта

**Freuly** — маркетплейс и платформа **лидогенерации для специалистов** (консультанты, психологи, смежные услуги и т.д.).

- **Публичные посетители** могут просматривать категории, карточки специалистов и **отправлять заявки (лиды) без регистрации**.
- **Специалисты** получают личный кабинет: профиль, услуги, публикация на витрине, работа с лидами.
- **Платформа** пересылает заявки специалистам и может уведомлять **владельцев/команду** через **Telegram**.
- Контент и интерфейс рассчитаны на **несколько языков** (маршруты с префиксом языка и переводы).

---

## 2. Технологический стек

| Компонент | Назначение |
|-----------|------------|
| **Next.js (App Router)** | Веб-приложение, SSR/маршруты, API routes |
| **Supabase** | PostgreSQL, Auth, Storage, при необходимости Edge Functions |
| **Vercel** | Хостинг и деплой |
| **Telegram Bot + Webhook** | Уведомления и интеграция с ботом |
| **Upstash Redis** | Распределённый rate limit для **публичных POST**-эндпоинтов |
| **Мультиязычность** | Сегмент `[lang]` в URL, таблицы переводов для части контента |

---

## 3. Основные роли

1. **Гость / клиент** — без аккаунта: поиск, карточки, отправка заявки.
2. **Специалист** — аккаунт Supabase Auth, дашборд, профиль и услуги.
3. **Администратор / владелец платформы** — защищённая админ-зона, API с токеном, модерация и настройки контента.

---

## 4. Основные маршруты и страницы

### Публичные страницы (высокоуровнево)

- **Главная (`/[lang]`, корень)** — витрина, популярные категории, рекомендуемые специалисты, блоки с `site-blocks`.
- **Страница категории** — список специалистов в категории (загрузка через API списка).
- **Профиль специалиста** — публичная карточка, услуги, отзывы, контакт/заявка.
- **Become specialist / для специалистов** — воронка регистрации и заявок.

### Кабинет специалиста

- Маршруты под `specialist/dashboard` (в т.ч. с языковым префиксом) — профиль, услуги, лиды, настройки.

### Админка

- `app/admin/...` — контент, специалисты, лиды и т.д. (доступ по механизмам проекта: токен, сессия).

### API (`app/api/...`)

- Публичные **GET**: категории, фильтры, список/поиск специалистов, рекомендации, профиль по id и др.
- Публичные **POST**: создание лида, заявки специалиста, регистрация, отзывы и т.д. (часть защищена rate limit).
- **Telegram webhook** — приём обновлений от Telegram.
- **Cron** (например, напоминания по лидам) — по секрету в заголовке.
- Загрузки файлов — аватары, галерея, документы, доказательства верификации, блоки сайта.

Подробная карта проекта: `docs/PROJECT_MAP.md`.

## 5. Обзор модели данных (концептуально)

| Сущность | Зачем нужна |
|----------|-------------|
| **specialists** | Учётная запись специалиста на витрине: статус, видимость, языки, геоданные, флаги (featured, founder и т.д.) |
| **specialist_services** | Услуги с ценой и привязкой к **категории услуги**; от этого зависят листинги и отображаемые цены |
| **specialist_profiles** | Расширенный профиль: город, о себе, фото, галерея, сертификаты и т.д. |
| **categories** | Категории (в т.ч. иерархия parent/child) |
| **leads** | Заявки от посетителей к специалистам |
| **Отзывы** | Таблицы статистики/отзывов (публичный GET отдаёт согласованно с модерацией) |
| **Таблицы переводов** | Локализация профиля и услуг (см. ADR-001) |
| **postal_codes** | Справочник для поиска по PLZ / локальной выдаче |
| **site_blocks** | Конфигурируемые блоки контента на главной и т.п. |

### Storage (бакеты в коде)

Примеры имён бакетов: `specialist-avatars`, `specialist-proofs`, `verification_docs`, `site-blocks` — загрузки идут через соответствующие API.

## 6. Правила публичной видимости специалиста

Публичная выдача должна быть **согласована** между списком категории, поиском, рекомендациями, профилем и картой.

Учитываются (в комбинации, по коду API):

- **status** — только из разрешённых для витрины статусов (`VISIBLE_PUBLIC_SPECIALIST_STATUSES` в коде).
- **is_active === true**
- **is_visible === true**
- **is_test** — тестовые аккаунты исключаются (`is_test` null или false), чтобы не светить тестовые данные публично.
- **Услуги** — для листингов по категории как правило нужны активные услуги с корректной ценой в контексте запроса (см. конкретный route).

Важно: многие публичные API используют **service role** на сервере, то есть **RLS не заменяет** явные фильтры в коде — их менять нужно везде одинаково.

---

## 7. Категории и услуги

- **Родительские и дочерние категории** — в API категорий учитывается иерархия (`parent_id`), режимы `parents` / `children`.
- **Услуги** определяют, попадёт ли специалист в выдачу по **категории услуги** и какая **минимальная цена** показывается (агрегация по строкам `specialist_services` в категории).
- У одного специалиста может быть **несколько строк** `specialist_services` в одной категории — это влияет на нагрузку запросов и на то, почему «постраничная выдача по строкам услуг» без дизайна опасна (см. ADR-002).

---

## 8. Лиды / заявки

- Публичное создание — типично **POST** на API лида (например `leads/create`).
- **Rate limiting** через **Upstash** (лимиты по IP и/или по специалисту — см. код маршрута и `lib/rate-limit/shared.ts`).
- При отсутствии переменных Upstash лимиты **отключаются (fail open)** — в продакшене переменные должны быть заданы.
- Уведомления **Telegram** владельцам/специалисту зависят от настроенных токенов и chat id (см. раздел про Telegram).
- В `leads/create` используется honeypot-поле `hp`: если оно заполнено, заявка отклоняется как спам.

---

## 9. Отзывы

- **Публичный GET** — отзывы с учётом видимости (показываются прошедшие модерацию / видимые).
- **Новый отзыв (POST)** — создаётся с **`is_visible: false`** до модерации.
- Перед созданием выполняется **проверка**, что специалист существует и доступен публично (логика в соответствующем route).

---

## 10. Интеграция Telegram

| Элемент | Назначение |
|---------|------------|
| **Webhook** | Маршрут API для приёма обновлений от Telegram |
| **TELEGRAM_BOT_TOKEN** | Токен бота (секрет; только сервер) |
| **TELEGRAM_WEBHOOK_SECRET** | Ожидаемое значение секрета; сверяется с заголовком **`X-Telegram-Bot-Api-Secret-Token`** |
| **TELEGRAM_OWNER_CHAT_IDS** | Список chat id для уведомлений владельцев (в коде `lib/telegram/sendMessage.ts`) |

**Токен и секрет нельзя** коммитить, отдавать в браузер или логировать. Отключение проверки секрета на webhook — критический риск (подделка запросов).

---

## 11. Уже проведённое усиление безопасности (high level)

- Секрет для **Telegram webhook** (заголовок `X-Telegram-Bot-Api-Secret-Token`).
- Убраны **отладочные утечки** (например, метаданные service key в публичных ответах категорий).
- Из публичного ответа профиля специалиста убран **`user_id`** (снижение риска связывания с аккаунтом).
- Ужесточены **отзывы** (публичная проверка специалиста, скрытый по умолчанию новый отзыв).
- **Фильтры** опираются только на публично видимых специалистов (включая исключение тестовых где применимо).
- **Upstash rate limiting** на выбранных **публичных POST** (лиды, регистрация, заявки, отзывы).
- Более **безопасные сообщения об ошибках** на части публичных API.
- В продакшене **не отдаётся `_trace`** из **`/api/specialists/list`** (отладка только вне production).

---

## 12. Ограничение частоты запросов (rate limiting)

- Переменные: **`UPSTASH_REDIS_REST_URL`**, **`UPSTASH_REDIS_REST_TOKEN`** (см. `.env.example`).
- Защищены в основном **публичные write**-эндпоинты (не GET discovery в текущей схеме).
- Если Redis не настроен — **fail open** (лимиты не применяются); для продакшена переменные должны быть заданы.
- Старый **in-memory** лимитер для лидов удалён, чтобы лимиты работали на **Vercel** при нескольких инстансах.

---

## 13. Производительность и кэширование

- Часть **публичных discovery GET** отдаётся с **Cache-Control** (CDN-friendly): фильтры, популярные категории, рекомендации, дерево категорий — см. `lib/http/cache.ts` и соответствующие routes.
- **`/api/specialists/list`** **не** кэшируется агрессивно намеренно (динамическая полнота выдачи и фильтры).
- Известное узкое место: список по категории может подгружать большой объём данных и пагинировать в памяти — **рефактор отложен**; см. **`docs/adr/002-specialists-list-pagination-performance.md`**.

## 14. Технический долг и будущая работа

- **`/api/specialists/list`**: в перспективе **SQL view/RPC** с **одной строкой на специалиста** и корректной пагинацией (ADR-002).
- Публичные чтения часто через **service role** — критичны **фильтры в приложении**; возможен обзор **RLS** в будущем.
- Возможные **GET rate limits** для anti-scraping (отдельное решение).
- **Индексы** БД под тяжёлые запросы — периодический пересмотр.
- **Оптимизация изображений** (`next/image` и т.д.) — по желанию продукта.

## 15. Переменные окружения (только имена, без значений)

### Supabase

- **`NEXT_PUBLIC_SUPABASE_URL`** — URL проекта.
- **`NEXT_PUBLIC_SUPABASE_ANON_KEY`** — анонимный ключ (клиент).
- **`SUPABASE_SERVICE_ROLE_KEY`** (или legacy **`SUPABASE_SERVICE_KEY`**) — серверный ключ с полным доступом; **только сервер**.

### Сайт и деплой

- **`NEXT_PUBLIC_SITE_URL`** — публичный URL сайта.
- **`APP_URL`** — альтернатива базовому URL в письмах/ссылках.
- **`VERCEL_URL`**, **`VERCEL_GIT_COMMIT_SHA`** — задаются Vercel при деплое.

### Админ API

- **`ADMIN_API_TOKEN`** — токен для защищённых admin API (`x-admin-token` / логика в `lib/adminApiAuth.ts`).

### Почта (Resend)

- **`RESEND_API_KEY`**
- **`MAIL_FROM`** или **`RESEND_FROM_EMAIL`**

### Telegram

- **`TELEGRAM_BOT_TOKEN`**
- **`TELEGRAM_WEBHOOK_SECRET`**
- **`TELEGRAM_OWNER_CHAT_IDS`**
- **`TELEGRAM_BOT_USERNAME`** (опционально, для UI)

### Upstash

- **`UPSTASH_REDIS_REST_URL`**
- **`UPSTASH_REDIS_REST_TOKEN`**

### Прочее

- **`CRON_SECRET`** — авторизация cron route (`Bearer`).
- **`TERMS_VERSION`**, **`SPECIALIST_RULES_VERSION`** — версии соглашений.
- **`CATEGORY_MIN_SPECIALISTS`**, **`NEXT_PUBLIC_CATEGORY_MIN_COUNT`** — пороги для категорий.
- **`DEV_ACCESS_KEY`** — опциональный доступ в dev через middleware.
- **`NEW_SPECIALIST_FUNNEL_ENABLED`**, **`NEW_SPECIALIST_DASHBOARD_ENABLED`**, **`FEATURED_HOME_BLOCK_ENABLED`**, **`PROGRAMMATIC_SEO_ENABLED`** — фичефлаги (`lib/featureFlags.ts`).
- **`NEXT_PUBLIC_ADMIN_IP_WHITELIST`** — опциональный whitelist IP.
- Для скриптов перевода и т.п. может встречаться **`DEEPL_API_KEY`** (не в `.env.example`, но в скриптах).

Полный ориентир: **`.env.example`** в корне репозитория.

## 16. Деплой

- Код в **Git** (обычно ветка **`main`**).
- **Vercel** подключается к репозиторию и собирает проект.
- Все секреты задаются в **настройках Environment Variables** на Vercel.
- После изменения env на Vercel часто нужен **редеплой**.
- Локально и в CI: **`npm run build`** должен проходить перед релизом.

## 18. Что нельзя менять «случайно»

- Возвращать **`user_id`** в публичных JSON профиля специалиста.
- Убирать фильтры **`is_test`** только в одном месте — правила должны совпадать между list/search/recommended/profile/map.
- Отключать проверку **`TELEGRAM_WEBHOOK_SECRET`** на webhook.
- Заменять **Upstash** на **in-memory** rate limit для продакшена на Vercel.
- Вешать **`.range()` напрямую на `specialist_services`** в `/api/specialists/list` как «быструю пагинацию» без дизайна «одна строка = один специалист» (см. ADR-002).
- Включать **`_trace`** в публичных ответах production.
- Менять правила **публичной видимости** в одном эндпоинте без сверки со всеми остальными.
