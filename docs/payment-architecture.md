# Payment Architecture

## 1. Purpose

Этот документ описывает **целевую продуктово-техническую архитектуру оплат Freuly** на этапе, когда реальные платежи ещё не включены. Он нужен, чтобы:

- заранее согласовать границы ответственности (продукт, биллинг, видимость, enforcement);
- не смешивать состояние подписки с публичным каталогом и логикой лидов;
- безопасно включать оплату через feature flags и поэтапный go-live.

**Документ не является спецификацией реализации** и не заменяет `docs/subscription-enforcement-policy.md`: enforcement и оплата описаны как **разделяемые оси**.

Ничего из этого файла **не обязано быть уже реализовано** в коде или БД.

---

## 2. Current state

На момент написания документа действует следующая базовая линия:

- **Платежи не принимаются**: нет checkout, нет webhook’ов от платёжного провайдера, нет боевых ключей в продуктовом потоке.
- **Страница pricing публичная и информационная**: объясняет тарифы, не создаёт платёжных обязательств и не ведёт к оплате без отдельного включения продукта.
- **Специалисты в основном в режиме early access** (или эквивалентном продуктовому состоянии): каноническое состояние подписки хранится в **`specialist_plan`** (`plan_code`, `plan_status`, `expires_at`, `grace_until` и связанные поля).
- **Админка** позволяет **вручную** управлять строкой `specialist_plan` (MVP-контроль без провайдера).
- **Display-state helper и subscription page в кабинете** отражают состояние подписки для специалиста, без привязки к живым платежам.
- **Enforcement** (автоматические санкции по подписке) **отдельно политикой** и на момент MVP может быть выключен или ограничен — см. policy-документ.

Итого: **источник истины по подписке — `specialist_plan`**; платежи пока не являются источником истины.

---

## 3. Core principles

1. **Никаких случайных платежей**  
   Пользователь не должен попасть на оплату без явного продукта и включённых флагов; кнопки «оплатить» не показываются, если оплата выключена.

2. **Оплата только при `PAYMENTS_ENABLED=true`**  
   Создание checkout-сессий, редиректы на провайдера и портал самообслуживания — только под флагом (и в сочетании с корректной конфигурацией провайдера).

3. **Автоматический enforcement только при `SUBSCRIPTION_ENFORCEMENT_ENABLED=true`**  
   Изменение видимости в каталоге, блокировки контактов, ограничения лидов и т.п. **не должны** включаться «само» из-за появления Stripe, если enforcement явно выключен.

4. **События провайдера → обновление `specialist_plan`**  
   Webhook и связанная логика **нормализуют** внешнее состояние во внутреннюю модель (`plan_code`, `plan_status`, даты). Публичные API не обязаны читать Stripe напрямую.

5. **Публичная видимость не зависит напрямую от Stripe**  
   Каталог, поиск, рекомендации опираются на **продуктовые поля и политику** (в т.ч. производные от `specialist_plan`), а не на «сырой» ответ API провайдера.

6. **Кабинет специалиста явно показывает платёжное/подписочное состояние**  
   После включения оплаты: понятный статус, даты, что делать при ошибке оплаты, ссылка на billing при включённом флаге.

7. **Юридическая и налоговая готовность до live-платежей**  
   Техническое включение оплаты не опережает Impressum, договорные условия, privacy, налоговые обязанности и процесс поддержки.

## 4. Feature flags

Все перечисленные флаги **по умолчанию `false`** (или эквивалент «выкл» в конфиге окружения), пока продукт явно не готов.

### `PAYMENTS_ENABLED`

- **Включает:** отображение точек входа в оплату (например, «Управление оплатой» / переход к checkout или billing), создание checkout-сессий и использование customer portal **в рамках защищённых API**, при наличии конфигурации провайдера.
- **Не включает:** автоматическое изменение видимости специалиста; автоматические ограничения лидов; webhook-обработку без отдельной готовности; юридический go-live.

### `SUBSCRIPTION_ENFORCEMENT_ENABLED`

- **Включает:** автоматическое применение правил из enforcement policy к видимости/лидам/контактам **на основе `specialist_plan`** (или согласованных производных).
- **Не включает:** приём платежей; создание подписок у провайдера; гарантию синхронности с Stripe (это зона биллинга и webhook).

### `SUBSCRIPTION_PUBLIC_PAID_COPY_ENABLED`

- **Включает:** публичный маркетинговый/UX-копирайт про «платные тарифы» на сайте (например, уточнённые формулировки на pricing, CTA к регистрации/кабинету), когда продукт готов это обещать.
- **Не включает:** реальную оплату без `PAYMENTS_ENABLED`; enforcement без `SUBSCRIPTION_ENFORCEMENT_ENABLED`.

### `BILLING_TEST_MODE` (или `STRIPE_MODE=test|live`)

- **Включает:** использование тестовых ключей, тестовых webhook endpoints, изоляцию тестовых специалистов/аккаунтов от боевых данных.
- **Не включает:** боевые списания; обязательность тех же путей в UI для всех пользователей (тест можно ограничить allowlist’ом).

**Важно:** флаги комбинируются. Типичный безопасный путь: сначала тестовый биллинг без enforcement, затем enforcement в staging, затем live платежи и поэтапно enforcement в prod.

## 5. Planned user flow

Целевой сценарий **после** включения оплаты:

1. Специалист видит **публичную pricing page** (информация о тарифах).
2. В **кабинете** открывает страницу подписки; если `PAYMENTS_ENABLED`, видит действие вроде «Оформить / Управлять оплатой» (копирайт согласуется отдельно).
3. По клику создаётся **checkout session** (или аналог) через защищённый backend; пользователь перенаправляется на провайдера.
4. После **успешной оплаты** возврат в кабинет (success URL); UI обновляет состояние после синхронизации с `specialist_plan`.
5. **Webhook** от провайдера фиксирует оплату/подписку и **обновляет `specialist_plan`** (и при необходимости связанные billing-таблицы).
6. Дашборд показывает актуальный **тариф и статус** (например, `active`, нужный `plan_code`).
7. При **неуспешной оплате** или просрочке webhook/провайдер инициируют переход к согласованным статусам (`grace_period`, `past_due` — если введён в модель, `expired`, `cancelled` и т.д.) **только в `specialist_plan` и сопутствующих полях**, без прямого воздействия на каталог, пока enforcement выключен.

Отдельно админ может по-прежнему **вручную** поправить `specialist_plan` (override), с аудитом и осторожностью — см. раздел про безопасность.

## 6. Planned routes

Ниже — **целевые** маршруты; на момент документа они **не обязаны существовать** или быть активными.

| Маршрут | Назначение |
|--------|------------|
| `/specialist/dashboard/billing` | Страница кабинета: статус подписки, ссылки на checkout/portal при `PAYMENTS_ENABLED`, история для специалиста (по мере появления данных). |
| `POST /api/billing/checkout` | Создание checkout session; только авторизованный специалист; **жёстко** завязан на `PAYMENTS_ENABLED` и валидацию тарифа. |
| `POST /api/billing/portal` | Создание сессии customer portal (управление платёжным методом, отмена и т.д.). |
| `POST /api/billing/webhook` | Приём событий провайдера; проверка подписи; идемпотентная обработка; **не** публичный анонимный «полезный» API — только провайдер. |

Пока оплата выключена, эти маршруты либо отсутствуют, либо возвращают 404/501 и не раскрывают внутреннюю логику.

## 7. Data model

**Базовый принцип:** `specialist_plan` остаётся **продуктовым каноном** подписки (`plan_code`, `plan_status`, `expires_at`, `grace_until`, …).

Опционально (на этапе реализации, не сейчас):

- **`billing_customer`** (или аналог): связь `specialist_id` ↔ `provider_customer_id`, валюта/регион по необходимости, метаданные для поддержки. Не смешивать с произвольными полями профиля специалиста.
- **`billing_events` / audit log**: сырые или нормализованные события webhook (тип, id события, payload hash, результат обработки) для расследований и идемпотентности.
- **Ссылки на инвойсы**: `invoice_id` / URL / статус последнего счёта — в отдельной таблице или в audit, а не размазанные по `specialists`.
- **Идентификаторы Stripe** (customer, subscription, price id): хранить **централизованно** в billing-слое, не разбрасывать по «случайным» колонкам `specialists`, чтобы не ломать публичные контракты и миграции.

Миграции и точная схема — на этапе реализации и после согласования с policy.

## 8. Stripe / provider events

Ориентировочный набор событий (названия Stripe; у другого провайдера — аналоги):

| Событие | Ожидаемое влияние на продукт (через обновление `specialist_plan`) |
|--------|---------------------------------------------------------------------|
| `checkout.session.completed` | Подтверждение успешной оплаты/старта подписки; выставить согласованные `plan_code`, `plan_status` (например `active` или `trialing`), обновить `expires_at` / `grace_until` по данным сессии/подписки. |
| `customer.subscription.created` | Инициализация или фиксация подписки; синхронизация периода и статуса. |
| `customer.subscription.updated` | Изменение плана, периода, статуса (trial → active, upgrade/downgrade); обновление дат и `plan_code`/`plan_status`. |
| `customer.subscription.deleted` | Окончание подписки; переход к `cancelled` / `expired` по правилам продукта и датам. |
| `invoice.payment_succeeded` | Подтверждение продления; продление `expires_at` (или эквивалент); сброс grace при необходимости. |
| `invoice.payment_failed` | Переход в предупреждающий статус (`grace_period`, `past_due` — если введён), установка `grace_until` по политике. |

Все переходы должны быть **идемпотентными** и **согласованы** с картой статусов (раздел 9).

## 9. Status mapping

**Пример** целевых соответствий (не финальный контракт до продуктового sign-off):

| Ситуация | Пример целевого `plan_status` / примечание |
|----------|---------------------------------------------|
| Успешная оплата, активный период | `active` |
| Триал у провайдера | `trialing` |
| Неуспешное списание | `grace_period` или отдельный будущий статус (`past_due`), согласовать с policy |
| Отмена в конце периода | `cancelled` с валидной `expires_at` до фактического окончания |
| Подписка удалена / окончена без продления | `cancelled` или `expired` по правилам продукта |

**Финальная карта статусов** должна быть:

- согласована с `docs/subscription-enforcement-policy.md`;
- зафиксирована до массового включения webhook в prod;
- покрыта тестами на уровне маппинга событий → `specialist_plan`.

## 10. Safety requirements

- **Проверка подписи webhook** (secret провайдера, допустимые версии API).
- **Идемпотентность**: повтор одного и того же события не должен дублировать побочные эффекты; хранить обработанные `event.id` (или эквивалент).
- **Структурированное логирование** без утечки PII/полных платёжных данных; корреляция по `specialist_id` / customer id.
- **Нет публичных неавторизованных billing API**, кроме webhook с проверкой подписи.
- **Админский override** сохраняется: ручные правки `specialist_plan` возможны; желательно логировать кто/когда (audit).
- **Нет деструктивного удаления** специалистов или профилей из потока биллинга; отмена подписки ≠ удаление пользователя.
- **Fallback при недоступности провайдера**: UI и продукт не должны «ломать» каталог; при сбое webhook — алерты, ручная сверка, при необходимости задержка enforcement.

## 11. Testing plan

- **Stripe Test Mode** (или тестовый контур провайдера).
- **Ограниченный набор тестовых специалистов** (фикстуры / отдельные аккаунты).
- **Тестовые карты** провайдера: успех, отказ, 3DS при необходимости.
- Сценарии: **успешная оплата**, **отказ**, **отмена подписки**, **replay webhook**.
- Проверка **дашборда** и **`specialist_plan`** после каждого сценария.
- Контроль: **публичная видимость и лиды не меняются** в ходе тестов, пока enforcement явно не включён для тестовой среды.

---

## 12. Go-live checklist

- **Gewerbe / правовая форма** и полномочия на приём платежей.
- **Impressum, AGB, privacy** обновлены под платежи и подписки.
- **Налоги / VAT / счета** (если применимо): кто выставляет, где хранятся, доступ специалиста.
- **Live-ключи** провайдера в защищённом хранилище секретов.
- **Live webhook URL** с мониторингом и ротацией secret.
- **Админка**: override и просмотр биллинг-состояния готовы к инцидентам.
- **Поддержка**: канал для споров по списаниям.
- **Коммуникация со специалистами** до включения платных тарифов.
- **Включение флагов по шагам**: сначала `PAYMENTS_ENABLED` без enforcement, затем мониторинг, затем при необходимости `SUBSCRIPTION_ENFORCEMENT_ENABLED`.

---

## 13. Explicit non-goals now

- Нет реальных платежей в prod «по умолчанию».
- Нет checkout и customer journey до включения флагов и готовности.
- Нет публичных webhook’ов без полного контура безопасности.
- Нет автоматического скрытия специалистов из каталога **только** фактом подключения Stripe.
- Нет изменений логики лидов и блокировок контактов **в рамках этого документа**; они остаются под enforcement policy.
- Нет удаления профилей/специалистов как способа «отмены подписки».

---

## 14. Recommended implementation order

1. Добавить **feature flags** в конфигурацию окружения и документацию.
2. Добавить **заглушку / disabled billing** в UI при выключенных платежах (понятное сообщение).
3. Подключить **конфиг провайдера** в режиме disabled/test (без боевых действий).
4. Реализовать **`/api/billing/checkout`** с жёсткой проверкой `PAYMENTS_ENABLED` и авторизации.
5. Реализовать **webhook** с проверкой подписи и идемпотентностью.
6. Ввести **маппинг событий → `specialist_plan`** и тесты.
7. Расширить **админку** просмотром биллинг-состояния (без утечки секретов).
8. Прогнать **полный цикл в test mode**.
9. Подготовить **юридический и налоговый** go-live.
10. Включить **live payments** и затем при необходимости **enforcement** по согласованному графику.
